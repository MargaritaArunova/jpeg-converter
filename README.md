# JPEG Compression Library

---

## Алгоритм JPEG (упрощённо)

```
Изображение (RGB)
      |
      v
1. Преобразование цветового пространства  RGB -> YCbCr
      |
      v
2. Разбивка на блоки 8x8 пикселей
      |
      v
3. Дискретное косинусное преобразование (DCT-II)  <-- основная вычислительная нагрузка
      |
      v
4. Квантование (lossy step — потеря информации)
      |
      v
5. Деквантование + обратный DCT (IDCT)
      |
      v
6. Восстановление изображения
      |
      v
7. Зигзаг-сканирование (готовит данные для энтропийного кодирования)
```

## Используемые механизмы синхронизации

| Файл | Примитив | Паттерн |
|---|---|---|
| `thread_pool.cpp` | `std::mutex` + `std::condition_variable` | Producer-consumer очередь задач |
| `thread_pool.h` | `std::packaged_task` + `std::future` | Получение результата асинхронной задачи |
| `color_converter.cpp` | `std::thread` + `join` | Fork-join: разбивка строк по потокам |
| `jpeg_encoder.cpp` | `std::thread` + `join` | Fork-join: разбивка блок-строк по потокам |
| `jpeg_encoder.cpp` | `std::atomic<int>` | Счётчик завершённых задач (без блокировки) |
| `benchmark.cpp` | `ThreadPool::submit` -> `std::future` | Пакетная обработка независимых изображений |

## Сборка

Требования: CMake >= 3.16, компилятор с поддержкой C++20 (GCC 10+, Clang 12+, MSVC 19.29+).

```bash
# В CLion: Run > Build  или  Build > Build Project
# Убедитесь, что выбрана конфигурация Release (не Debug)

# Из терминала:
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
./build/jpeg_converter          # запуск с авто-определением числа ядер
./build/jpeg_converter 8        # явно задать максимальное число потоков
```

> **Важно**: бенчмарки нужно запускать в **Release**-сборке.
> В Debug-режиме оптимизации отключены — разница между Sequential и Parallel
> будет существенно меньше из-за накладных расходов на вызов функций.

## Серии экспериментов

Три параметра: число потоков (1-8 и 16), размер изображения (8x8 ... 2048x2048, степени двойки)
и размер блока ДКП (4x4 ... 128x128, степени двойки; в стандартном JPEG блок 8x8).
Сценарии: `dct_threads` (std::thread), `dct_pool` (ThreadPool), `color` (RGB -> YCbCr,
от блока не зависит), `batch` (4 изображения через ThreadPool), `amdahl`, а также
`sequential` — последовательная базовая линия.

```bash
cmake -B cmake-build-release -DCMAKE_BUILD_TYPE=Release
cmake --build cmake-build-release -j
pip install -r experiments/requirements.txt

# Проверка пайплайна на уменьшенной сетке (~1 минута, паузы отключены):
python3 experiments/run_experiments.py --build-dir cmake-build-release --quick --runs 1 --out /tmp/quick

# Быстрая серия (~15 минут): картинки 8/64/512/2048, блоки 8/16/64, потоки 1-8 и 16,
# 5 прогонов, пауза 90 с между прогонами. batch считается без 2048x2048.
python3 experiments/run_experiments.py --build-dir cmake-build-release --preset fast

# Полная серия (много часов): 9 размеров картинки x 6 размеров блока, паузы 120 с / 15 с.
python3 experiments/run_experiments.py --build-dir cmake-build-release
# Если прервали — продолжить с того же места (с теми же параметрами):
python3 experiments/run_experiments.py --build-dir cmake-build-release --preset fast --resume

# Усреднить прогоны и построить графики:
python3 experiments/plot_results.py
```

Результаты:

- `experiments/raw/run_K/<сценарий>.csv` — сырые данные каждого прогона
  (`scenario,image_size,block_size,threads,reps,time_ms`; `threads = 0` — последовательная версия,
  `block_size = 0` — сценарий не зависит от блока). Короткие замеры повторяются внутри процесса,
  пока сумма не достигнет 50 мс, `time_ms` — среднее по этим повторам.
- `experiments/results/summary_<сценарий>.csv` — среднее и стандартное отклонение по прогонам.
- `experiments/plots/<сценарий>/time_grid.png`, `speedup_grid.png` — по панели на размер картинки,
  линия на размер блока; `by_size/` — то же отдельными файлами.

Для честных замеров закройте тяжёлые программы, подключите питание и не трогайте ноутбук во время серии.

## Пять сценариев и их выводы

### Сценарий A — DCT-сжатие, большое изображение (2048x2048)

**Суть метода сжатия.**
Изображение делится на блоки 8×8 пикселей. К каждому блоку применяется
дискретное косинусное преобразование (ДКП-II): пространственные значения яркости
и цвета переводятся в набор из 64 частотных коэффициентов. Первый коэффициент
(DC) отражает среднюю яркость блока, остальные (AC) — детали разной частоты.
Затем коэффициенты делятся на значения из таблицы квантования и округляются —
это единственный необратимый шаг, уменьшающий точность данных. Высокочастотные
коэффициенты (мелкие детали, почти неразличимые глазом) делятся на большие
числа и обнуляются, что даёт сжатие. После квантования выполняется обратный
ДКП: изображение восстанавливается с потерями.

**Почему хорошо параллелится.**
Каждый блок 8×8 обрабатывается полностью независимо от соседних: нет общих
коэффициентов, нет зависимостей по данным. Это классическая **embarrassingly parallel**
задача. Блок-строки изображения делятся между потоками — каждый поток читает
и пишет в свой диапазон памяти без конкуренции.

**Ожидаемый результат**: почти линейное ускорение. На 4 потоках ~3.8x, на 8 потоках ~7x.

---

### Сценарий B — То же DCT-сжатие, но на маленьком изображении (64x64)

**Суть метода сжатия.**
Алгоритм тот же, что в сценарии A: ДКП → квантование → обратный ДКП для каждого
блока 8×8. Разница только в размере изображения: 64×64 пикселя дают всего 64 блока
суммарно по всем каналам — ничтожно малый объём работы.

**Почему параллелизм вредит.**
Создание одного потока ОС занимает ~50–200 мкс. Сжатие 64 блоков занимает меньше.
При запуске 4 потоков программа тратит больше времени на запуск и остановку потоков,
чем на само вычисление. Параллельная версия оказывается заметно **медленнее** последовательной.

**Вывод**: параллелизм оправдан только тогда, когда объём работы существенно
превышает стоимость создания потоков (~50–200 мкс на поток).

---

### Сценарий C — Преобразование цветового пространства RGB → YCbCr (2048x2048)

**Суть метода сжатия.**
Перед ДКП JPEG переводит пиксели из RGB в цветовое пространство YCbCr:
- **Y** — яркость (luma): несёт основную зрительную информацию.
- **Cb, Cr** — цветоразностные компоненты (chroma): описывают оттенок.

Человеческий глаз в 2–4 раза хуже различает цветовые детали, чем детали яркости.
Поэтому к Cb и Cr применяют более грубое квантование, чем к Y, — это один из
главных источников сжатия JPEG без заметной потери качества для наблюдателя.
Формула преобразования: линейная комбинация R, G, B по коэффициентам BT.601,
применяемая независимо к каждому пикселю.

**Почему ускорение меньше, чем в сценарии A.**
Операция на пиксель — всего несколько умножений и сложений, почти нет вычислений.
Задача ограничена не процессором, а **пропускной способностью памяти**: все потоки
одновременно читают и пишут в один массив пикселей, конкурируя за шину памяти.
Добавление потоков перестаёт давать прирост после насыщения шины.

**Ожидаемый результат**: ускорение есть, но меньше линейного и достигает плато раньше сценария A.

**Вывод**: параллелизм эффективнее для **compute-bound** задач (ДКП), чем для **memory-bound** (конвертация цвета).

---

### Сценарий D — Пакетная обработка через ThreadPool (16 изображений 512x512)

**Суть метода сжатия.**
Каждое из 16 изображений проходит полный JPEG-конвейер: преобразование цвета →
ДКП всех блоков → квантование → обратный ДКП → восстановление. Алгоритм тот же,
что в сценарии A, но применяется не к одному большому изображению, а к пакету
независимых изображений поменьше. Типичный пример — конвертация фотоальбома
или обработка кадров видеопотока.

**Почему хорошо параллелится.**
Изображения не имеют общих данных: каждое живёт в своём буфере памяти, никаких
зависимостей между ними нет. Это **task-level parallelism** — параллелизм на уровне
задач. ThreadPool создаёт потоки один раз при запуске и переиспользует их для всех
16 задач, избегая накладных расходов на создание потока для каждого изображения.

**Ожидаемый результат**: почти линейное ускорение — близко к сценарию A.

**Вывод**: ThreadPool — правильный паттерн для очереди однородных независимых задач.

---

### Сценарий E — Закон Амдала: параллельный ДКП + последовательное зигзаг-сканирование (2048x2048)

**Суть метода сжатия.**
После ДКП и квантования все 64 коэффициента блока 8×8 нужно упорядочить
перед отправкой в энтропийный кодировщик. Для этого используется **зигзаг-обход**:
коэффициенты считываются по диагонали — от DC (верхний левый угол, низкая частота)
к самым высокочастотным (правый нижний угол). После квантования высокочастотные
коэффициенты обычно равны нулю, поэтому в зигзаг-порядке они образуют длинные
серии нулей в конце массива. Эти серии компактно кодируются алгоритмом Хаффмана:
кодировщик строит оптимальное prefix-free дерево по всему потоку данных и выдаёт
битовый поток, где частые символы кодируются короче. Хаффман **последователен по
природе**: длина кода символа N зависит от всей таблицы, построенной на предыдущих
данных, поэтому параллельно закодировать независимые блоки и склеить потоки
без разрывов не получается.

**Почему ускорение ограничено.**
~80% работы — ДКП-блоки, они параллельны. ~20% — зигзаг-сканирование + имитация
последовательного прохода, который нельзя распараллелить. Закон Амдала даёт
жёсткий теоретический потолок:

```
S(N) = 1 / (p_seq + p_par / N)   где p_seq = 0.20, p_par = 0.80

S(2)  = 1 / (0.20 + 0.80/2)  = 1.67x
S(4)  = 1 / (0.20 + 0.80/4)  = 2.50x
S(8)  = 1 / (0.20 + 0.80/8)  = 3.08x
S(∞)  = 1 / 0.20             = 5.00x  (абсолютный максимум при любом числе потоков)
```

**Вывод**: даже при идеальном параллелизме оставшиеся 20% последовательного кода
не позволят получить ускорение больше 5x — независимо от числа ядер процессора.

## Таблица сравнения методов

| Этап JPEG | Параллелизуем? | Почему |
|---|---|---|
| Преобразование RGB->YCbCr | Да (хорошо) | Каждый пиксель независим |
| Выделение блоков 8x8 | Да (отлично) | Нет зависимостей между блоками |
| DCT 8x8 | Да (отлично) | Embarrassingly parallel |
| Квантование | Да (отлично) | Каждый коэффициент независим |
| Зигзаг-сканирование | Нет (плохо) | Последовательный обход, нужен для Хаффмана |
| Кодирование Хаффмана | Нет | Данные следующего символа зависят от предыдущего |
| Маленькие изображения | Нет (вредно) | Накладные расходы > полезная работа |

## Ключевые концепции

1. **Fork-join** (`color_converter.cpp`, `jpeg_encoder.cpp`)  
   Разбиваем данные на N чанков -> создаём N потоков -> ждём всех через `join()`.

2. **Producer-consumer с condition_variable** (`thread_pool.cpp`)  
   Рабочие потоки спят на `condition_variable::wait`, просыпаются при появлении задачи в очереди.

3. **std::future / std::packaged_task** (`thread_pool.h`)  
   Позволяют получить результат асинхронной задачи без явных общих переменных.

4. **std::atomic** (`jpeg_encoder.cpp`)  
   Инкремент счётчика без мьютекса — достаточно для простых счётчиков.

5. **Закон Амдала** (`benchmark.cpp`, сценарий E)  
   Последовательный фрагмент кода ограничивает максимальное ускорение независимо от числа потоков.
